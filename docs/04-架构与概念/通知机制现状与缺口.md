# 通知机制：现状与缺口

> 概念文档（explanation）。这一篇解释**为什么**通知这样设计、**现在实际落地成什么样**、**缺口在哪**、以及对你联调意味着什么。要动手改通知，见后续 `02-开发指南`（待建）。

---

## 设计初衷：为什么要"应用内通知"

在架构设计 v1.1（第 8 章）里，通知被定位成**小程序内的轻量消息系统**：

- 任务被指派给你、任务状态变更、任务开始前提醒时，在「消息中心」留下一条记录。
- 首页 TabBar 显示红点，点进去能看到历史、可回溯、不打扰。
- 不依赖微信的下发通道，不会因为用户没开订阅就彻底收不到。

设计上认为这是最适合学生团队内部工具的形态：消息可查、可归档，负责人也能据此确认"通知有没有触达"。

与之相对的是**微信订阅消息**——那是微信的对外开放通道，好处是不用自己建消息中心，坏处是：用户必须**提前授权**、且一次性订阅通常只能发一次、未授权就完全收不到。

> 设计文档在第 8.6 节明确把方案从"订阅消息"改成了"小程序内通知"。**但代码没有跟上这个决定**——这是当前最大的认知陷阱，下面细说。

---

## 实际落地：只剩一个订阅消息云函数

代码里与通知相关的只有 `cloudfunctions/sendNotification/index.js`，它做一件事：

```javascript
// 简化逻辑
await cloud.openapi.subscribeMessage.send({
  touser: openid,
  templateId: TEMPLATE_IDS[type],   // ⚠️ 三个都是占位符
  page: `pages/task-detail/index?taskId=${taskId}`,
  data: { ...拼接的模板字段 }
});
```

也就是说，**实际实现走的是订阅消息通道，不是设计里说的应用内通知**。它被 `createTask`、`updateTask` 在内部异步调用（任务指派、任务取消时），也可以由前端直接调。

### 两个关键缺口（务必知道）

| # | 缺口 | 现状 | 后果 |
|---|------|------|------|
| 1 | **模板 ID 是占位符** | `TEMPLATE_IDS` 三个值都是 `your-template-id-*`（`TODO`） | 实际发送时 `subscribeMessage.send` 必然失败。代码已 `try/catch` 静默跳过，**不报错、只计为未发送** |
| 2 | **不写 `notifications` 集合** | 函数只发订阅消息，没有任何 `db.collection('notifications').add(...)` | 而 `app.js` 的红点逻辑依赖**读** `notifications` 集合 → 消息中心永远空、红点永远不亮 |

缺口 2 尤其坑：设计想要"应用内通知"，前端也按这个写了（消息中心页面 + 红点），但**后端从没往那个集合里写过数据**。所以前端 UI 是个没有数据源的空壳。

## 订阅消息机制的硬约束

即便把模板 ID 填上了，订阅消息本身也有无法绕开的规则，联调时要心里有数：

- **用户必须先授权**：调 `wx.requestSubscribeMessage` 拿到一次授权后，才能发一条对应类型的消息。没授权的用户，代码会静默跳过（不发也不报错）。
- **一次性为主**：非"长期订阅"类模板，一次授权通常只能发一次。任务提醒这类需要反复触达的场景，订阅消息并不理想——这正是设计当初想改用应用内通知的原因。
- **异步触发、不可控**：`sendNotification` 由其他云函数在后台异步调用，你不会在前端直接拿到"是否送达"的结果，只能看到 `createTask` 返回的 `taskId`（通知发送成功与否不影响任务创建）。

## 对你的联调意味着什么

| 你想联调的目标 | 现实 | 建议预期 |
|----------------|------|----------|
| 看"红点 + 消息中心"有没有新消息 | 永远没有（集合无数据） | 别在这上面耗时间；这是设计-实现落差，不是你配错了 |
| 收一条任务指派提醒 | 模板 ID 占位 → 静默失败 | 先到微信公众平台申请 3 个订阅消息模板，替换占位符后才有机会收到 |
| 验证"通知已发送"的返回 | `sendNotification` 返回 `{ code:0, data:{sent,total} }`，但 `sent` 可能因模板/授权为 0 | 以 `sent` 与 `total` 的差值判断，别只看 `code:0` |

> 📌 经验法则：当前阶段把通知当成"**尽力而为、不可观测**"的能力。任何功能流程都**不该**依赖通知成功才能继续（任务创建/状态变更本身不依赖通知结果，这点设计是对的）。

## 补完路径（给想修这个的人）

要真正对齐设计，两条路线，按需选：

**路线 A：只修订阅消息（最小成本）**
1. 到 [微信公众平台 → 订阅消息](https://mp.weixin.qq.com) 申请 3 个模板（对应 `task_assigned` / `task_reminder` / `task_cancelled`），拿到真实 `templateId`。
2. 替换 `sendNotification/index.js` 里 `TEMPLATE_IDS` 的三个占位值。
3. 前端在合适时机（如首次进入、任务创建后）调 `wx.requestSubscribeMessage` 引导授权。
> 缺点：仍是一次性订阅，反复提醒场景体验差，且未授权收不到。

**路线 B：实现设计里的"应用内通知"（对齐架构设计）**
1. `sendNotification` 在发订阅消息的同时，**写一条记录到 `notifications` 集合**（字段建议：`userId, type, taskId, title, read:false, createdAt`）。
2. `app.js` 已有读 `notifications` 判红点的逻辑，确认集合名、字段对齐即可点亮红点。
3. 消息中心页面读 `notifications` 渲染列表，点击置 `read:true`。
> 这样才真正落地设计意图：消息可回溯、不依赖微信授权。

> 无论走哪条，都建议把"通知机制现状"同步回架构设计文档（当前 8.6 与代码矛盾），避免后来人再踩一次。
