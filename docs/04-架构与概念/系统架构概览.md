# 系统架构概览

> 概念文档（explanation）。这一篇帮你建立对系统"长什么样、数据怎么流、权限怎么管"的**心智模型**。具体怎么部署、怎么调接口，看 [快速上手](./../01-快速上手/getting-started.md) 和 [API 参考](./../03-参考文档/api-reference.md)。

---

## 一句话模型

这是一个**无独立后端的微信小程序**：前端跑在微信里，所有服务端逻辑都是**云函数**，所有数据都存在**云数据库**。微信云开发（CloudBase）把"服务器 + 数据库 + 存储"打包成了托管服务，团队不需要自己运维。

---

## 三层结构

```
┌─────────────────────────────────────────────┐
│  微信小程序前端（miniprogram/）               │
│  - 页面 (pages/) + 组件 (components/)         │
│  - TDesign 组件库                            │
│  - utils/api.js：统一封装云函数调用           │
│  - config/env.js：按 envVersion 选云环境      │
└───────────────┬─────────────────────────────┘
                │  wx.cloud.callFunction({ name, data })
                ▼
┌─────────────────────────────────────────────┐
│  云函数层（cloudfunctions/，10 个已实现）       │
│  login / verifyKey / createTask / updateTask  │
│  getTasks / updateUserStatus / getDutySchedule│
│  createLocation / getLocations / sendNotification│
│  （6 个规划中：generateKey / scheduleNotify /  │
│   getReport / crawlNews / getNewsCache /       │
│   exportReport）                              │
└───────────────┬─────────────────────────────┘
                │  cloud.database() / cloud.openapi()
                ▼
┌─────────────────────────────────────────────┐
│  云开发底座（CloudBase）                       │
│  - 云数据库集合：users / tasks / user_status  │
│    / locations / keys                         │
│  - 云存储（图片等）                            │
│  - 订阅消息通道（sendNotification 用）         │
└─────────────────────────────────────────────┘
```

要点：
- **前端从不直接连数据库**，所有读写都过云函数。云函数里用 `cloud.getWXContext().OPENID` 拿到调用者身份，再做权限判断。
- **环境隔离靠 `config/env.js`**：开发者工具=dev、体验版=test、正式版=prod，当前三者指向同一个真实环境 `cloud1-d8gdddel1d4b1cea1`（见 [快速上手·环境配置](./../01-快速上手/getting-started.md#环境配置-dev--test--prod)）。

## 权限模型：四级角色

系统的访问控制不是"登录/未登录"二元，而是基于 `users.role` 的四级：

| 等级 | role | 能做什么 |
|------|------|----------|
| 1 | `member` 普通成员 | 看自己的任务、改自己的状态、确认/开始/完成任务 |
| 2 | `photo_director` / `video_director` 部门主任 | 在等级 1 基础上：创建/编辑任务、管理部门机位、看本部门数据 |
| 3 | `center_director` 视觉中心主任 | 看全部数据、跨部门任务 |

**两个关键设计点**：
1. **角色靠密钥升级**：初始都是 `member`，主任/中心负责人用一次性密钥（`verifyKey`）把角色升上去。密钥由 `generateKey` 生成——**该函数尚未实现**，当前 `keys` 集合需手动维护（见 [API 参考·未实现](./../03-参考文档/api-reference.md#未实现云函数-6-个)）。
2. **权限在云函数内校验**：前端无法绕过，因为身份来自 `OPENID`，不是前端传的字段。

## 学期隔离：数据按学期分桶

所有业务数据（任务、人员状态等）都带一个 `semester` 字段，格式为 `2026-spring`（**英文**，不是设计稿里的中文"2026-春季"）。逻辑上每个学期是一批独立数据，避免历史数据污染当前学期。

> 这意味着换学期时，统计、任务列表等会自然切到新桶——前提是创建数据时正确写入 `semester`（云函数已自动填当前学期）。

## 关键数据流（以"建任务→成员确认"为例）

```
主任在 createTask 填表
   │  wx.cloud.callFunction('createTask')
   ▼
createTask 云函数：校验角色≥2 → 写 tasks(status=pending) → 异步调 sendNotification
   │                                         │
   ▼                                         ▼
assignedTo 成员登录小程序               订阅消息（模板占位→静默失败；若实现应用内通知→写 notifications）
   │  getTasks(myTasks:true)
   ▼
getTasks 云函数：按 OPENID 收窄范围 → 返回该成员的任务
   │  成员点"确认" → updateTask({status:'confirmed'})
   ▼
updateTask 云函数：校验是 assignedTo 本人 → 改状态 → 触发取消时再通知
```

更完整的时序见 [sequence-diagram.mermaid](./../sequence-diagram.mermaid)（⚠️ 注意：该图 4.2 仍画"订阅消息"，与已定的"应用内通知"方案不符，属过期内容）。
