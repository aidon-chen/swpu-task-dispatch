# 环境初始化清单（M10-3）

本清单用于在新环境（dev / test / prod）首次搭建时，按顺序完成数据库、索引、初始账号与发布前开关的初始化。
三个环境互相隔离（数据库、云函数、存储互不相通），**每个环境都应独立执行一遍本清单**。

> ⚠️ 生产环境（prod）严禁执行会清空/覆盖已有数据的操作。下方所有步骤均为「幂等 / 仅新增」，可安全重跑。

---

## 0. 前置条件

| 项 | 说明 |
| --- | --- |
| 云环境已创建 | 微信开发者工具 → 云开发 → 分别创建 dev / test / prod 三个环境，复制各自「环境 ID」填入 `config/env.ids.js` |
| 云函数已部署 | 见 `scripts/deploy-functions.js`：`node scripts/deploy-functions.js --env <dev\|test\|prod>` |
| 域名已配置 | 小程序后台 → 开发管理 → 开发设置 → 服务器域名：request/upload/download 均指向云开发默认域名（通常无需手填，云函数走内网） |

---

## 1. 集合创建（幂等，可重复执行）

调用云函数 `initDatabase`（每个环境各跑一次）。该函数在 `REQUIRED_COLLECTIONS` 中列出全部集合，已存在则跳过，**不会删除或覆盖数据**。

需存在的集合：

| 集合 | 用途 |
| --- | --- |
| `users` | 用户信息（openid / 部门 / 角色 / 学期） |
| `keys` | 权限密钥（一次性，一密钥一用户） |
| `tasks` | 任务（含任务模板，`isTemplate=true` 区分） |
| `user_status` | 成员出勤状态 |
| `locations` | 拍摄机位 |
| `notifications` | 通知记录 |
| `duty_schedule` | 值班排班矩阵（userId × date） |
| `news_cache` | 新闻匹配缓存（按 taskId） |

> 触发方式：在开发者工具「云开发 → 云函数 → initDatabase → 测试」中手动触发，或在代码中 `wx.cloud.callFunction({ name: 'initDatabase' })`。

---

## 2. 推荐索引（性能 / 避全表扫描）

`initDatabase` 当前**不创建索引**，请在云开发控制台「数据库 → 集合 → 索引管理」手动补齐（每个环境都要建）：

| 集合 | 索引字段 | 说明 |
| --- | --- | --- |
| `users` | `openid`（唯一） | 登录/查角色高频 |
| `tasks` | `isTemplate` | 列表默认排除模板 |
| `tasks` | `status` | 状态筛选与统计 |
| `tasks` | `assignedTo` | 成员看自己任务 |
| `tasks` | `creatorId` | 主任看本部门 |
| `tasks` | `ownerDepartment` | 模板按部门可见 |
| `tasks` | `semester` | 学期归档 |
| `keys` | `key`（唯一） | 密钥校验 |
| `keys` | `isUsed` | 是否已使用 |
| `notifications` | `userId` + `isRead` | 通知列表/未读数 |
| `duty_schedule` | `userId` + `date` | 排班矩阵查询 |
| `user_status` | `userId` | 成员状态查询 |

> 建议后续把索引创建固化进 `initDatabase`（用 `db.createIndex` 或控制台导出再导入），避免每次手工遗漏。

## 3. 初始主任账号（每个环境）

普通成员由 `login` 自动注册（默认 `role: member`）。首位**视觉中心主任（center_director）**需在环境搭建时落地，可选两种方式：

**方式 A（推荐，走正式密钥流程）：**
1. 用任意已登录账号调用 `generateKey({ role: 'center_director' })` 生成正式密钥。
2. 在目标环境的小程序里「验证密钥」完成绑定，该用户即成为中心主任。
3. 之后主任可继续 `generateKey` 生成摄影部/视频部主任密钥，逐级下放。

**方式 B（紧急/自动化）：**
- 云开发控制台 → 数据库 → `users` → 找到目标用户 → 直接把 `role` 改为 `center_director`、`department` 设为 `''`（中心主任无部门限制）。

> ⚠️ 测试环境可用 `generateTestKey` 生成 `DEV-` 前缀的可复用测试密钥；**生产环境绝不使用测试密钥**，且 `generateTestKey` 的测试开关在发布前必须关闭（见第 5 节）。

---

## 4. 初始密钥策略

| 环境 | 测试密钥（generateTestKey） | 正式密钥（generateKey） |
| --- | --- | --- |
| dev | 可开启（方便本地联调） | 可用 |
| test | 可开启（体验版验收用） | 可用 |
| prod | **必须关闭** | 仅主任可生成，按需发放 |

---

## 5. 发布前开关检查（上线前必做）

`code` 与「测试模式」相关的开关在上传正式包（release）前**必须全部归位 false**，否则云端会信任前端传入的调试角色，存在越权风险。

| 文件 | 字段 | 期望值 |
| --- | --- | --- |
| `miniprogram/config/test.js` | `enabled` | `false` |
| `miniprogram/config/test.js` | `features.debugLogin` | `false` |
| `miniprogram/config/test.js` | `features.testKeyMultiUse` | `false` |
| 各云函数 `testConfig.js`（createTask / createLocation / getReport / exportReport / generateKey / updateDutySchedule / getTemplates） | `enabled` | `false` |
| 同上 | `allowDebugRoleOverride` | `false` |

> 可用全局搜索 `enabled: true` 快速核对，确保正式分支无残留 `true`。

## 7. 一键部署命令速查

```bash
# 部署全部函数到测试环境
node scripts/deploy-functions.js --env test

# 只部署单个函数（调试用）
node scripts/deploy-functions.js --env test --name createTask

# 先 dry-run 确认命令，不实际执行
node scripts/deploy-functions.js --env prod --dry-run
```

> 脚本内部只连接 `--env` 指定的单一环境，不会跨环境批量写，符合 M10-2 的隔离要求。
