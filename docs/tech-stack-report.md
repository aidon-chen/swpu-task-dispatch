## 2. 关键选型对比

### 2.1 小程序框架：微信原生 vs uni-app vs Taro

#### 方案概览

| 维度 | 微信原生 | uni-app | Taro |
|------|----------|---------|------|
| **开发语言** | WXML + WXSS + JS | Vue.js（推荐） | React / Vue |
| **学习曲线** | ⭐⭐ 低（微信生态标准） | ⭐⭐⭐ 中（需Vue基础） | ⭐⭐⭐⭐ 较高（React+构建工具） |
| **包体积** | 极轻（无框架开销） | 中等（框架runtime ~50KB） | 较大（React runtime ~100KB） |
| **性能** | ⭐⭐⭐⭐⭐ 原生，无中间层 | ⭐⭐⭐⭐ 接近原生 | ⭐⭐⭐ 有编译转换损耗 |
| **微信API兼容** | ⭐⭐⭐⭐⭐ 第一时间支持 | ⭐⭐⭐⭐ 需等待适配 | ⭐⭐⭐ 部分API需自行封装 |
| **云开发集成** | ⭐⭐⭐⭐⭐ 原生支持 | ⭐⭐⭐ 需额外配置 | ⭐⭐⭐ 需额外配置 |
| **多端复用** | ❌ 仅微信小程序 | ✅ 一套代码8端 | ✅ 一套代码多端 |
| **社区生态** | ⭐⭐⭐⭐⭐ 官方支持+最大社区 | ⭐⭐⭐⭐ 活跃社区 | ⭐⭐⭐⭐ 京东维护 |
| **招聘难度** | 易（前端+小程序基础即可）| 中（需Vue+uni-app经验）| 较高（需React+Taro经验） |

#### 选型结论：✅ 微信原生

**选择理由**：
1. **本项目的多端需求为零** — 目标用户明确是微信用户，无需支付宝/抖音/百度小程序适配
2. **与云开发无缝集成** — `wx.cloud.callFunction()` 原生支持，无需额外封装
3. **2MB包大小限制** — 原生无框架开销，有利于控制在2MB以内。uni-app和Taro的运行时+组件库会占据100-200KB
4. **团队能力匹配** — 开发投入为个人/小团队，原生学习成本最低
5. **API第一时间兼容** — 微信新API原生框架第一时间支持，跨端框架需等待适配层更新
6. **调试便利性** — 微信开发者工具原生支持，云函数调试/数据库查看一体化

> ⚠️ **风险提示**：若未来需要扩展到其他小程序平台（如支付宝/抖音），需重构。但根据需求分析，40人内部工具无此扩展需求。

### 2.2 后端方案：云开发 vs 自建服务器（Express/Koa）

#### 方案概览

| 维度 | 微信云开发（CloudBase） | 自建服务器（Express/Koa） |
|------|------------------------|--------------------------|
| **服务器运维** | ✅ 零运维，全托管 | ❌ 需购买服务器、配置Nginx、部署监控 |
| **微信生态集成** | ⭐⭐⭐⭐⭐ 原生wx.cloud API | ⭐⭐ 需手动对接微信API |
| **鉴权体系** | 自动获取openid，无需自建 | 需自建JWT/OAuth2.0体系 |
| **数据库** | 云数据库（MongoDB兼容），自动扩容 | 需自建MySQL/MongoDB，手动运维 |
| **文件存储** | 云存储内置CDN | 需对接OSS/COS，配置域名 |
| **消息推送** | 云调用直接发订阅消息 | 需对接微信服务端API |
| **定时任务** | 云函数定时触发器 | 需配置cron（node-cron/PM2） |
| **域名备案** | ❌ 无需（云开发自带域名） | ❌ 需域名+备案（耗时2-4周） |
| **SSL证书** | ❌ 自动管理 | ❌ 需手动申请+续期（Let's Encrypt或购买） |
| **扩容能力** | 自动扩容，按量付费 | 需手动扩容/负载均衡 |
| **开发速度** | ⭐⭐⭐⭐⭐ 开箱即用 | ⭐⭐ 需搭建基础设施 |

#### 成本对比（月度）

| 费用项 | 云开发 | 自建服务器 |
|--------|--------|-----------|
| **服务器** | 免费额度内¥0（超出按量） | 最低¥50-100/月（2C4G云服务器） |
| **数据库** | 包含在免费额度内 | 自建免费，云数据库¥30+/月 |
| **域名+SSL** | ¥0 | ¥50-100/年（域名）+ 免费SSL |
| **存储/CDN** | 包含在免费额度内 | ¥5-20/月（OSS按量） |
| **运维人力** | ¥0 | 运维时间 ≈ ¥500+/月（折算人工） |
| **月均总成本**（40人） | **¥0-30** | **¥100-600** |

#### 选型结论：✅ 微信云开发（CloudBase）

**选择理由**：
1. **零运维负担** — 40人内部工具，全托管架构使团队专注业务开发
2. **微信生态原生集成** — 云调用（订阅消息）、自动openid获取、数据库权限天然隔离
3. **成本极低** — 40人规模基本在免费额度内运行（详见第4章成本估算）
4. **开发速度** — 无需搭建服务器、配置数据库、申请域名备案（省2-4周）
5. **自动扩容** — 无需担心学期末稿分统计高峰期的并发压力

> ⚠️ **风险提示**：云开发锁定微信生态，若未来需要Web管理后台，需额外方案。应对策略：云函数可被外部HTTP调用（需开启HTTP访问），可复用于Web端。

### 2.3 图表库：wx-charts vs ECharts for 微信小程序 vs AntV F2

#### 方案概览

| 维度 | wx-charts | ECharts（echarts-for-weixin） | AntV F2（@antv/f2） |
|------|-----------|------------------------------|---------------------|
| **体积** | ⭐⭐⭐⭐⭐ ~20KB（极轻） | ⭐⭐ ~500KB+（需精简到~300KB） | ⭐⭐⭐ ~180KB |
| **Canvas渲染** | ✅ 原生 | ✅ 通过echarts-for-weixin适配 | ✅ 原生Canvas |
| **动画效果** | ⭐⭐ 基础动画 | ⭐⭐⭐⭐⭐ 丰富动画和交互 | ⭐⭐⭐⭐ 流畅动画 |
| **图表类型** | 折线图、柱状图、饼图、环形图、面积图、雷达图 | 40+种图表（全能型） | 折线图、柱状图、饼图、面积图、散点图等10+种 |
| **自定义能力** | ⭐⭐ 有限 | ⭐⭐⭐⭐⭐ 极强（option配置） | ⭐⭐⭐⭐ 强 |
| **学习曲线** | ⭐⭐ 低（配置简单） | ⭐⭐⭐⭐ 中高（需理解option） | ⭐⭐⭐ 中 |
| **小程序适配** | ⭐⭐⭐⭐⭐ 专为小程序设计 | ⭐⭐⭐ 需echarts-for-weixin组件包裹 | ⭐⭐⭐ 需自行封装组件 |
| **触摸交互** | ⭐⭐ 有限 | ⭐⭐⭐⭐ 完善 | ⭐⭐⭐⭐ 完善 |
| **2MB包占用** | ~20KB | ~300KB（经裁剪） | ~180KB |

#### 本项目图表需求分析

| 需求 | 图表类型 | 复杂度 |
|------|----------|--------|
| 月度参与次数趋势 | 折线图 | 基础 |
| 学期参与次数对比 | 柱状图 | 基础 |
| 任务类型分布 | 饼图 | 基础 |
| 部门成员工作量对比（主任视图） | 横向柱状图 | 中等 |

#### 选型结论：✅ wx-charts

**选择理由**：
1. **体积优势决定性** — 仅20KB，在2MB小程序包限制下极为友好。ECharts精简后仍需300KB，占15%；F2需180KB占9%
2. **需求匹配度100%** — 本项目仅需折线图、柱状图、饼图三种基础图表，wx-charts完全覆盖
3. **原生Canvas实现** — 无第三方依赖，渲染性能最优
4. **配置简单** — 学习成本低，符合当前项目的快速开发定位
5. **专为小程序优化** — 与微信Canvas API完美兼容，无适配问题

**不选ECharts/AntV F2的理由**：
- 功能过剩：40+图表类型在本项目中仅需3种，性价比极低
- 体积过大：在2MB限制下，图表库占大量空间会严重挤压业务代码
- 复杂度高：option配置学习成本高，调试困难

> 📌 **若未来需要复杂图表**（如热力图、关系图），可在后续版本按需引入ECharts的自定义构建（仅引入所需图表类型裁剪到~150KB）。

### 2.4 爬虫库：axios + cheerio vs Puppeteer

#### 方案概览

| 维度 | axios + cheerio | Puppeteer |
|------|----------------|-----------|
| **运行方式** | HTTP请求 + HTML解析 | 启动完整浏览器（Chromium） |
| **内存消耗** | ~20MB | ~300MB+（含Chromium进程） |
| **执行速度** | ⭐⭐⭐⭐⭐ 秒级 | ⭐⭐ 需等待页面加载+JS执行 |
| **动态页面支持** | ❌ 不支持JS渲染 | ✅ 支持SPA/JS动态渲染 |
| **反爬对抗** | ⭐⭐ 基础请求头伪装 | ⭐⭐⭐⭐ 可模拟真实用户行为 |
| **部署难度** | ⭐⭐⭐⭐⭐ 极简（npm install） | ⭐ 极难（需Chromium ≥200MB） |
| **云函数兼容** | ✅ 完美兼容 | ❌ 云函数256MB内存不够 |
| **资源消耗** | 极低 | 极高（CPU+内存） |
| **维护成本** | 低 | 高（Chromium版本管理） |

#### 目标网站分析

| 分析项 | 详情 |
|--------|------|
| 目标URL | https://www.swpu.edu.cn/news/yw.htm |
| 页面类型 | 服务端渲染（SSR）新闻列表页 |
| 内容特征 | 静态HTML，新闻列表为 `<li>` 结构 |
| 翻页方式 | URL参数（`index.htm` → `index_2.htm`），非Ajax |
| 动态内容 | 无（无React/Vue客户端渲染） |

#### 选型结论：✅ axios + cheerio

**选择理由**：
1. **目标网站为静态SSR页面** — 无需执行JavaScript即可获取完整内容
2. **云函数环境限制** — 云函数默认256MB内存，Puppeteer的Chromium进程需要300MB+，无法部署
3. **执行效率高** — 单次爬取耗时<3秒（含礼貌性延迟），用户等待体验好
4. **接近零维护** — cheerio基于jQuery语法，代码简洁，新闻页面结构变更时修改成本极低
5. **成本友好** — 不消耗额外云函数内存配额

**Puppeteer仅需考虑的极端场景**（当下不适用）：
- 目标网站改为SPA动态渲染 → 此时需要Puppeteer，但云函数无法支持，需迁移到云托管（支持Docker）
- 当前应对：PRD已预留「手动输入新闻链接」作为反爬问题的备选方案

### 2.5 中文分词：jieba（@node-rs/jieba） vs nodejieba

#### 方案概览

| 维度 | @node-rs/jieba | nodejieba |
|------|---------------|-----------|
| **实现方式** | Rust原生模块（N-API） | C++原生模块（NAN） |
| **分词速度** | ⭐⭐⭐⭐⭐ 极快（Rust） | ⭐⭐⭐⭐ 快（C++） |
| **安装方式** | npm install，预编译二进制 | npm install，需本地编译 |
| **Node.js兼容** | 14.x / 16.x / 18.x ✅ | 14.x / 16.x ✅，18.x ⚠️ |
| **云函数兼容** | ✅ 支持预编译 | ⚠️ 云函数Serverless环境可能编译失败 |
| **包体积依赖** | ~5MB（预编译） | ~10MB（含编译依赖） |
| **API风格** | Promise（现代） | Callback（传统） |
| **维护状态** | 🔥 活跃（2024仍在更新） | 🟡 维护模式 |
| **分词准确率** | 与nodejieba一致（同词库） | 基准 |

#### 选型结论：✅ @node-rs/jieba

**选择理由**：
1. **云函数部署友好** — 预编译二进制，npm install即可用，nodejieba在Serverless环境可能因缺少C++编译链而失败
2. **Rust实现更可靠** — 内存安全，无C++内存泄漏风险
3. **Promise API** — 与云函数async/await风格一致
4. **持续维护** — 社区活跃，Node.js版本升级时同步适配
5. **分词质量一致** — 使用相同词库，准确率无差异

> 📌 **备选方案**：若@node-rs/jieba出现兼容问题，可降级使用 `jieba-wasm`（纯WebAssembly实现，兼容性最好但速度略慢），或使用简单的关键词匹配（无需分词依赖）。

### 2.6 日期处理：dayjs vs moment

#### 方案概览

| 维度 | dayjs | moment |
|------|-------|--------|
| **体积** | ⭐⭐⭐⭐⭐ ~2KB（核心） | ❌ ~70KB（不可树摇） |
| **2MB包占用** | ~2KB | ~70KB（3.5%） |
| **API兼容** | ⭐⭐⭐⭐ 95%与moment一致 | ⭐⭐⭐⭐⭐ 基准 |
| **不可变性** | ✅ 所有操作返回新对象 | ❌ 可变操作（易出bug） |
| **时区支持** | 插件（~2KB） | moment-timezone（~100KB+） |
| **Tree Shaking** | ✅ 支持 | ❌ 不支持 |
| **维护状态** | 🔥 活跃 | 🟡 维护模式（官方推荐替代品） |
| **小程序适配** | ✅ 完美 | ⚠️ 体积过大 |

#### 选型结论：✅ dayjs

**选择理由**：
1. **体积优势压倒性** — 2KB vs 70KB，在2MB小程序包限制下dayjs占0.1%，moment占3.5%
2. **API几乎相同** — 迁移成本为零，`dayjs().format()` 与 `moment().format()` 用法一致
3. **不可变性更好** — `.add(1, 'day')` 返回新对象，避免意外修改原值的bug
4. **Moment官方已不推荐自身** — Moment.js维护者推荐使用dayjs/Luxon等替代品
5. **小程序场景足够** — 本项目仅需日期格式化、时间差计算、学期判断，dayjs完全覆盖

## 5. 限制与风险

### 5.1 微信小程序包大小限制

| 限制项 | 限制值 | 影响范围 | 应对措施 |
|--------|--------|----------|----------|
| 主包总大小 | **≤ 2MB** | 所有页面、组件、工具函数 | 见下方详述 ⬇️ |
| 单个分包 | **≤ 2MB** | 每个分包独立限制 | 使用分包加载策略 |
| 总包大小（含分包） | **≤ 20MB** | 全部代码+资源 | 40人项目无需担心 |

**2MB包体积预算**：

| 组成部分 | 预估大小 | 占比 | 说明 |
|----------|----------|------|------|
| 页面WXML+WXSS | ~50KB | 2.5% | 12个页面的模版和样式 |
| 页面JS逻辑 | ~200KB | 10% | 12个页面的业务逻辑 |
| 组件代码 | ~80KB | 4% | 4个公共组件 |
| 工具函数（utils/） | ~40KB | 2% | api.js, auth.js, date.js, storage.js, notification.js, crawler.js |
| wx-charts | ~20KB | 1% | 图表库 |
| dayjs（核心+时区） | ~5KB | 0.25% | 日期库 |
| WeUI组件库 | ~150KB | 7.5% | 微信官方UI库 |
| 小程序基础运行时 | ~350KB | 17.5% | 框架必需 |
| **已用合计** | **~895KB** | **44.75%** | — |
| **剩余空间** | **~1153KB** | **55.25%** | 预留给功能迭代和资源文件 |

**控制策略**：
1. **图片不进包** — 所有图标使用微信原生icon或SVG，大图用云存储远程加载
2. **代码压缩** — 开发者工具自动压缩上传，实际包体积会更小
3. **分包加载**（预留） — 若2MB不够，可将低频页面（如机位详情、新闻匹配）放入分包
4. **按需引入WeUI** — 只引入实际使用的组件而非全量
5. **避免node_modules进包** — 云函数依赖在云端安装，不占用小程序包体积

> ✅ **结论**：当前设计下包体积预估~800-900KB，占限额44%，有充足余量应对后续功能迭代。

### 5.3 爬虫合规风险及应对

#### 风险清单

| 风险 | 严重度 | 概率 | 描述 |
|------|--------|------|------|
| IP被封禁 | 🔴 高 | 🟡 中 | 高频爬取导致学校网络防火墙封禁云函数出口IP |
| 页面结构变更 | 🟡 中 | 🟡 中 | 学校网站改版导致cheerio选择器失效 |
| 法律合规 | 🟢 低 | 🟢 低 | 仅内部使用，非商业目的 |
| 数据时效性 | 🟡 中 | 🟡 中 | 新闻发布延迟，任务后7天内可能尚未上线 |

#### 具体应对措施

**1. IP封禁风险应对**：
```
✅ 缓存机制：同一任务24小时内仅爬取1次，30天缓存有效期
✅ 礼貌延迟：每页请求间隔1.5秒，避免连续高并发
✅ 请求头伪装：设置常见浏览器User-Agent
✅ 仅爬取必要数据：新闻列表+正文前500字，不爬取全站
✅ 失败降级：爬取失败时提示"网络繁忙，请稍后重试"
✅ 手动备选：始终提供手动输入新闻链接功能
```

**2. 页面结构变更应对**：
```javascript
// 防御性编程示例
try {
  const newsItems = $('.news-list li')  // 主要选择器
  if (newsItems.length === 0) {
    // 降级选择器
    newsItems = $('.list-item, .article-item, .news-item')
  }
  if (newsItems.length === 0) {
    // 全量降级
    return { code: 3, message: '暂无法匹配新闻，网站结构可能已变更，请手动搜索' }
  }
} catch (e) {
  return { code: 3, message: '解析失败，请稍后重试' }
}
```

**3. 法律合规应对**：
```
✅ 仅爬取公开新闻列表（非登录后内容）
✅ 仅用于内部稿分统计，不对外传播
✅ 仅存储标题+链接，不存储新闻全文
✅ 目标网站robots.txt遵守检查（虽然高校网站通常无限制）
✅ 爬取频率低（用户手动触发，非定时全量爬取）
```

**4. 爬虫可用性保障 — 多重降级路径**：

```
用户点击"匹配新闻"
    │
    ├── 路径A：缓存命中 → 直接返回（最快）
    │
    ├── 路径B：爬取成功 → 返回结果 + 写缓存
    │
    └── 路径C：爬取失败
          ├── C1：返回友好提示 + "手动输入链接"入口
          ├── C2：返回空结果 + "建议到新闻网搜索"
          └── C3：记录错误日志供后续排查
```

### 5.4 其他技术风险

| 风险 | 影响 | 应对 |
|------|------|------|
| 订阅消息授权率低 | 成员错过任务通知 | 小程序内消息中心 + 首页待办红点提醒 |
| 微信登录获取信息受限 | 需手动填写昵称/头像 | 新版本微信仅返回默认昵称，需提供手动编辑入口 |
| 云数据库查询性能 | 聚合查询慢 | 建立合理索引 + 分页加载（每页20条） |
| 云函数冷启动延迟 | 首次调用慢1-2秒 | 用户体验可接受，高频函数可设置预置并发（付费） |
| iOS底部安全区 | 底部导航被遮挡 | 使用 `safe-area-inset-bottom` CSS变量适配 |
