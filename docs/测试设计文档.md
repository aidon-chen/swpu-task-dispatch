## 1. 测试分层策略

小程序 + 云开发的特殊性：前端跑在微信双线程运行时（无法 `require` 直接跑），云函数跑在 Node（可本地 `require` 单测）。据此分四层：

| 层级 | 名称 | 运行环境 | 工具 | 速度 | 维护成本 | 当前状态 |
|------|------|----------|------|------|----------|----------|
| L0 | 前端逻辑单测 | Node + 全局 mock(`wx`/`getApp`/`Page`) | 原生 `assert` | 快 | 低 | ✅ login / testMode |
| L1 | 云函数单测 | Node + `wx-server-sdk` mock（内存库） | 原生 `assert` | 快 | 低 | ✅ 7 个函数 |
| L2 | 模拟器 E2E | 微信开发者工具模拟器 + automator | 见 §6 | 慢 | 中 | ⚠️ 手动为主 |
| L3 | 真机/评审清单 | 真机预览 + 人工 | 检查表 | 最慢 | — | 📋 见 §7 |

**原则**：业务逻辑（权限、字段合并、通知触发、状态机）尽量下沉到 L1 云函数单测——它们最稳定、最快、最容易 CI；纯 UI 交互留给 L2/L3。

## 2. 测试基础设施

### 2.1 云函数 Mock 底座 `tests/_mockCloudSdk.js`
拦截 `require('wx-server-sdk')`，提供：
- 内存集合：`where`(支持 `_.neq/gte/lte/lt/in/eq`、**链式 `.and()`**、`$or`)、`orderBy`、`limit`、`skip`、`field`、`count`、`get`、`add`、`doc().get/update/remove`
- `db.RegExp` 关键词匹配
- `cloud.getWXContext()` → 默认 `OPENID:'test-openid'`；可用 `setWXContext(ctx)` 覆盖（测试"缺失身份"分支）
- `cloud.callFunction()` → 记录调用日志（`getCallLog()`），可对**跨函数调用**断言（如 createTask 是否真调了 sendNotification）；内置分支：`sendNotification`/`login` 返回 canned response，`getReport` **委托真实 getReport 逻辑**（保证 exportReport 测试拿到真实统计）
- `axios` 桩：拦截 `require('axios')`，`get(url)` 从 `setFakeHttp(map)` 注册表返回 HTML 字符串（值为 `Error` 实例则抛错），供 `crawlNews` 离线端到端单测
- `cheerio` 不拦截，使用真实包（已作为 devDependency 安装），供 `extractContent` 与 `doCrawl` 解析假 HTML

### 2.2 运行方式
```bash
# 全量
node tests/runAll.js
# 单文件
node tests/scheduleNotify.test.js
```
> 注意：仓库根为 `miniprogram/`，测试内相对路径统一用 `../cloudfunctions/...`、`../pages/...`（历史遗留的 `../miniprogram/` 前缀已全部修正）。

### 2.3 编写一个新云函数测试的标准模板
```js
const assert = require('assert');
const { installMock, getMockDb, seed, getCallLog, clearCallLog }
  = require('./_mockCloudSdk.js');
installMock();
const fn = require('../cloudfunctions/xxx/index.js').main; // 注意是 .main
const db = getMockDb();
// seed({ users:[...], tasks:[...] }); fn({ ...event }); assert...
```

现状只有 `login` 有单测。其余页面建议分两类处理：

- **有纯逻辑、可抽的函数**（优先 L0）：`create-task` 的 `validateForm`/`onSelectTemplate` 已 E2E 验证过，可抽成纯函数补 L0；`messages`（消息中心）、`statistics`（统计）的格式化函数。

## 6. 模拟器 E2E（L2）方案

用微信开发者工具 + `miniprogram-automator`（`connect({ wsEndpoint:'ws://127.0.0.1:9420' })`）。建议脚本化场景：
1. 调试登录 → 以 center_director 进入 → 建任务 → 校验消息中心出现通知。
2. 存为模板 → 从模板创建 → 校验字段继承。
3. 切换普通成员 → 校验看不见他人任务。

> ⚠️ 已知坑：外部改文件/部署云函数会触发 DevTools 重编译，**撕掉自动化扩展上下文**，导致 bridge/SDK 报 `Extension context invalidated`。恢复需重启模拟器或重开 DevTools，纯环境问题非代码 bug。

## 7. 通知功能专题测试（你之前专门问的）

系统**不依赖微信订阅消息**，改走「小程序内消息中心」：`sendNotification` 写 `notifications` 集合，前端 `messages` 页展示。`scheduleNotify` 由定时器每 30 分钟扫描。

**三层测法：**
1. **L1 单测（已实现）**：`scheduleNotify.test.js` 用相对当前时间的种子覆盖「开始前 2h 提醒 / 过期自动完结 / 幂等防重」；`sendNotification.test.js` 覆盖写入与文案。
2. **L2 模拟器**：调试登录 → 建一个 startTime=“2 小时后”的任务 → 等定时器或手动触发 `scheduleNotify` → 消息中心应出现“任务即将开始”。
3. **L3 手动**：真机预览，建任务指派给自己，确认收到站内提醒；把任务 endTime 设过去，确认被自动置为 completed。

## 8. CI 与提交门禁建议

- `tests/runAll.js` 作为**提交前必跑**（pre-commit hook 或 CI 单测步）。
- 云函数部署前（`scripts/deploy-functions.js`）先跑单测，失败不部署。
- **发布前强制**：所有 `testConfig.js` 与 `config/test.js` 的 `enabled` 必须恢复 `false`（见 `状态快照.md` 与 `MEMORY.md` 的“云环境策略”）。

## 9. 已知约束 / 坑

- Mock 库**不校验字段类型、不实现事务、不实现服务端 `serverDate` 真实序列化**——仅保证逻辑分支正确。
- `db.RegExp` 仅做字符串 `test`，不支持云端全文索引语义。
- 跨函数调用断言依赖 `cloud.callFunction` mock 的分支（`sendNotification`/`login` 返回 canned response，`getReport` 委托真实逻辑），新增跨调函数需在 mock 里补对应分支。
- 前端单测无法覆盖 WXML 渲染与 `setData` 真实桥接，这部分必须由 L2/L3 兜底。
